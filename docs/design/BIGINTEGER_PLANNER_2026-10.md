# ACO 2.0 計算器の再設計

日付: 2026-10-03 / 関連: [Issue #218](../issues/ISSUE-218.md)

状態: graph.2-local開発候補まで実装。標準加工パターンの共有カタログを追加。完成条件は未達。
graph.1はユーザーが配置済みで起動障害を報告。graph.2の配置・起動・実機受入は未実施。
実装範囲、設計との差分、残る制約は [実装記録](GRAPH_PLANNER_IMPLEMENTATION_2026-10.md) を参照。
設計根拠は現行APIのソースと末尾の一次資料。性能の数値は受入目標であり、達成実績ではない。

## 1. 決定

BigInteger APIの互換性だけを固定し、計算方式、内部クラス、VM採用、スレッド構成、キャッシュを再設計する。
採用する方式は、**共有するパターングラフの需要集約と、競合する部分の整数制約計算**。
パターンの入力・出力個数は定数。注文量、在庫量、製造回数が注文ごとに変わる値である。

- 固定の工程は、共通素材の需要を合算してから一度だけ計算する。
- 複数製法、代替材料、複数出力による選択は、一つの収支モデルとして同時に扱う。
- 触媒、返却容器、循環には、開始時に必要な在庫と工程順序を付ける。
- 純粋な計算中はWorld、Grid、Provider、RecipeManagerを参照しない。
- 通常数量も巨大数量も同じ計算器を通し、すべての会計量をBigIntegerで保持する。
- 実行と計画は別の仕事。機械の速度、投入間隔、電力を計画器が変更しない。

本体はJavaで実装し、通常グラフは配列上の整数計算で処理する。
競合部分の整数制約にはSMTInterpolを直接利用する。[R4]
旧VMやrc.4計算器を第2の実行経路として残さない。試験用グラフの計測は実装記録に記載し、実機の性能受入とは分ける。

## 3. 注文の流れ

```mermaid
flowchart LR
  P[パターン登録・変更] --> C[不変のパターンカタログ]
  Q[計画ボタンをサーバーが受信] --> S[在庫・権限・カタログを固定]
  C --> S
  S --> G[共有グラフを取得・構築]
  G --> E[需要集約と必要な整数制約計算]
  E --> R[数量と工程順序を持つ計画]
  R --> A[既存BigInteger APIと計画画面]
  A --> U[ユーザーが製作開始]
  U --> X[AE2・外部CPUが実在庫を確保して実行]
```

計画の時点T0は、サーバーが要求を受け付けてスナップショットを作る時点。
クライアントのクリック時刻と、通信遅延をまたいで完全一致するとは定義しない。
計画はT0の情報に対する回答であり、計画画面を開いている間の材料予約ではない。

### カタログ

Providerの登録・変更で、パターンを不変の`PatternDef`へ変換する。
入力候補、NBT、単位、全出力、返却規則、Providerの順序・識別情報を保持する。
同じ定義は共有するが、Providerの優先順位や可視性が異なるものまで同一化しない。
変更時は変更した定義とその依存索引だけを更新する。[R1][R2]

ゲーム起動時には登録イベントから構築する。注文のたびに全レシピデータベースを走査しない。
新規登録処理のコストも測定し、注文前へ移した費用を「消えた負荷」として扱わない。
パターン定義の世代と、それから作るコンパイル結果の世代を対応させる。
コンパイルが未完了なら、T0で保持した不変定義から計算ワーカーが構築する。
T0後に取得した可変情報を、T0の情報として扱わない。

### スナップショット

サーバー所有の境界で、在庫、Requesterの権限、利用可能Provider、emitter設定を取得し、
その時点のカタログ参照とまとめて`OrderSnapshot`にする。
BigInteger在庫Providerがある場合は正確な数量を取り込む。
完全性が確認できないlong投影を、正確な巨大在庫として採用しない。

在庫は注文ごとに一度取得する。計算中の在庫変動で注文を取り消したり取り直したりしない。
キャッシュするのはパターン構造と定数演算であり、「この在庫なら何個作れる」という無条件の回答ではない。
同じ注文の再表示は計画結果を再利用する。別注文には新しい在庫を渡す。

### MOD固有の入力

標準加工パターンは、登録された入力・出力数量をそのまま使う。
MekanismやGTの機械内部のレシピ探索は、クラフト計画の入力にはしない。
標準作業台、NBT置換、耐久値変化、返却品は、それぞれ純粋な規則へ変換するアダプターを持つ。
組合せで返却品が変わる場合、スロットを独立だと仮定せず、組合せ全体の効果を表す。

未知のJavaコールバックを単に「定数」とみなしてキャッシュしない。
実環境で使うパターン型はすべてアダプター対象にし、ワーカーへWorld参照を渡さずに結果を再現する。
任意のWorld依存コールバックを一般的に定数化できるとは約束しない。
未対応型はパターンID・型を特定した未対応結果にし、素材不足や製作可能へ読み替えない。
受入対象の実パターン集合で未対応が0になるまで完成条件は満たさない。

## 4. グラフと数量の表現

アイテム等の正確なキーとレシピを別々のノードにする二部グラフを使用する。
レシピは入力集合と全出力集合を持つ。副産物を別の独立レシピに分割しない。[R3]
キーの同一性には種類、NBT、fluid/chemical等の区別を含める。

ホットループではキーを`int`のIDへ変換し、隣接関係を平坦な配列に格納する。
`int`は配列添字専用。需要、在庫、製造回数、入出力、返却、bytesはBigInteger。
符号付きの収支差分もBigIntegerを使う。浮動小数点を数量会計へ入れない。

注文対象から到達する定義を共有ノードとして構築する。
複数の経路から同じ素材へ来ても、ノードと定義を複製しない。
十分な在庫で下流展開を省略する場合も、未知の製法を「製法なし」と記録しない。
不足が出た時に同じ不変カタログから必要部分を追加し、既に構築した部分は使い回す。

## 5. 固定工程の需要集約

製法が一つで、出力の結合や返却による順序問題がない部分は、完成品側から原料側へ処理する。
全消費側からの需要が揃ってから、その素材の在庫を一度だけ差し引く。

```text
need[k]   = すべての消費側から集まった需要
take[k]   = min(stock[k], need[k])
deficit   = need[k] - take[k]
runs[r]   = ceilDiv(deficit, outputPerRun[r, k])
need[in] += runs[r] * inputPerRun[r, in]
surplus[k]= runs[r] * outputPerRun[r, k] - deficit
```

製法がない原料なら`missing[k] = deficit`で完了する。
在庫不足で例外を投げて、最初からもう一度不足シミュレーションを回す構成にはしない。
中間在庫、ロット端数、余剰をノードに残す。原料まで展開した係数だけに潰さない。
既存完成品を取り出すだけで注文完了にしないよう、根の要求は「新規製作」として扱う。

例: `G = 16A + 16B + 16C`、A/B/C各1個にWを2個、`3 iron -> 4 W`。
Gを1個ならW需要は96個、W製造24回、iron72個。
Wが5個、ironが65個なら、W製造23回、iron必要69個、不足4個、W余剰1個。
この計算でA/B/CごとにW製造を切り上げると結果が変わるため、需要合算を先に行う。

固定工程の計算は固有ノード・辺の数に比例するBigInteger演算で行う。
数量が増えると整数の桁数に応じた費用は増えるが、注文個数ぶんループしない。

## 6. 複数製法・副産物・共用在庫

全レシピを一つずつ試して下流を再帰展開せず、競合する範囲の式を一度組む。
レシピ回数`n[r]`と必要な代替入力の割当を未知数にする。
入力・出力個数は登録パターンから来る定数のまま扱う。

```text
n[r] >= 0, n[r] は整数
0 <= used[k] <= stock[k]
used[k] + missing[k] + emitted[k]
  + sum_r((out[k,r] + returned[k,r] - in[k,r]) * n[r])
  = requested[k] + remaining[k]
remaining[k] >= 0
```

この式は数量保存の条件。第7節の開始条件・順序条件も計画に含める。
`emitted`は捕捉済みのemitter契約に許されたキーだけに定義する。
代替入力は各スロットの使用回数合計が`n[r]`と一致するように制約する。
返却が入力の組合せに依存するレシピは、組合せ単位の効果を使う。

`3 ore -> 2 A + B`でA4個とB2個を要求した場合、同じ`n[r]=2`が両方を満たす。
独立してA用2回、B用2回とは計上しない。

SCCによる循環分割だけで独立性を判断しない。
例えばAにironかcopper、Bにironが必要で、在庫がiron1・copper1なら、両方を同じ制約範囲へ入れる。
これによりAをcopper、Bをironで作れる。同じironを二重に割り当てたり、先にAへ割り当てて不足と決めたりしない。
共有する有限資源、返却品、出力を介して競合する部分は結合する。
大きな結合領域が残る可能性はある。SCCで必ず小さくなるとは仮定しない。

固定部分は整数の切上げと中間在庫の式を保持したまま消去・共有する。
未知の需要が流れ込む境界は、式として制約範囲へ含める。
各部分を独立に最適化して、後から在庫の矛盾を直す方式にはしない。

### 解の選択と不足

第一問は`missing=0`で成立する計画の有無。成立したら実行可能な計画を返す。
最少電力や最少工程の世界最適解を探し続ける機能は追加しない。
Providerの優先順位と候補順は、実行可能な解同士の選好として使う。
別の利用可能な製法を含めて作れる場合に、優先製法の不足だけで終了しない。

不足が必要な場合も、同じグラフ・制約を再利用して不足許可へ切り替える。
不足を許す場所は原料の終端と循環の起動材。完成品そのものを架空に追加して解を作らない。
最終的な不足は選択した工程順序の開始必要量から算出する。
不足表示はその具体的な製法の追加材料であり、全製法横断の最小不足とは表示しない。
アイテム1個と液体1mBを単純に足した目的関数で製法を決めない。

不要な余分の製造は需要への寄与がない工程を除去し、成立する範囲で製造回数を縮約する。
通常工程は第5節の最小ロット回数を厳守する。複数出力のロット余剰は正確に表示する。
制約計算は既存の整数エンジンへ任せ、BigInteger対応の汎用SAT/ILPソルバーを自作しない。
SMTへ渡すのは定数係数の線形整数式と選択条件。未知数どうしの乗算を混ぜない。
数量をbitvectorへ変換して固定幅化せず、数学的な整数として渡す。
`SAT`でも順序が未構成なら計算中、`UNKNOWN`は計算不能・中断の結果であり、不足の証明には使わない。
無在庫で失敗した結果を、在庫のある別注文へ再利用しない。

## 7. 触媒・返却品・循環

収支が0の触媒でも、最初に1個必要な場合がある。
`catalyst + ore -> catalyst + plate`は、catalyst在庫0で開始できない。
最終収支だけで可否を決められない点はPetri netの研究でも扱われている。[R5]

各工程列には、正確な収支`delta`と、途中で一度も不足しないための開始必要量`seed`を持たせる。
これを計画構築中に集計する。別のシミュレーターで全個数を再生し直さない。
以下は、入力と出力の効果が固定された工程列に対する本設計の式である。

```text
単一工程: delta = output + return - input; seed = input
Aの後にB: delta = deltaA + deltaB
           seed = max(seedA, seedB - deltaA, 0)  // キーごと
同じ列をn回 (n >= 1):
           deltaN = n * delta
           seedN  = seed + max(0, -(n - 1) * delta)
n = 0:     deltaN = 0; seedN = 0
```

触媒が戻る同一工程を巨大回数繰り返しても、開始必要量は1個のまま。
一方、毎回失われる原料は回数に比例する。容器が戻る前に再利用する順序は許可しない。
耐久値やNBTが変わる場合は別のキー・状態として扱い、同じ固定効果の繰返しへ偽装しない。

循環はSCCに切り分け、起動工程、繰返し列、終了工程として記録する。
`A -> B`、`B + ore -> A + plate`なら、Aを種にした2工程の繰返しとして圧縮できる。
種Aがない場合、起動材を供給する実際の別工程が必要になる。

一般の循環では、収支解から実際に並べられる工程列を構成し、行き詰まった局所部分を再探索する。
行き詰まりの事実だけを根拠に、その製造回数の全順序を不可能と断定しない。
独立工程の順序違いは共有し、固定効果の繰返しは上の式で圧縮する。
必要条件として成立する制約だけを追加する。探索中・不明を素材不足へ変換しない。

任意の循環が常に短い列に圧縮できる、あるいは必ず10秒で解けるとは主張しない。
参考のCEGAR手法自身にも一般的な終了保証がない。[R5]
受入対象に含まれる循環を具体的に列挙し、順序まで解けることを完成条件に含める。
この箇所と、未対応の動的パターンは、設計上もっとも検証が必要な部分である。
途中の候補に対する不足と、全選択を考慮した不足を区別する。
解けない循環を見つけただけで、別の起動製法や順序まで不可能と決めない。

## 8. スレッド、キャッシュ、APIへの返却

要求は一度だけAE2の計算用実行枠へ渡す。計算タスクから別の計算タスクを起動しない。
グラフ処理、整数制約、結果集計は同じワーカーで進める。
複数注文は既存実行枠で並行できるが、各注文の可変在庫とソルバー状態は共有しない。
SMTInterpolのインスタンスは各ワーカーの実行中注文が所有し、複数スレッドで同時に触らない。
キャンセルは通常のタスク取消に接続し、ソルバーの終了要求まで届かせる。

共有キャッシュは、カタログから作る不変のグラフ・式に限定する。
古い世代は利用中注文がなくなった時に解放する。無制限の注文結果キャッシュを設けない。
巨大な全組合せ表や全経路表を先に作らない。

計画は`patternTimes`等の数量に加え、選んだ実入力、返却、Provider候補、圧縮した工程順序を持つ。
集計値から別の計算器で製法を選び直す処理をなくす。
`exactBytes`は外部CPUと合意した容量式で算出する。内部グラフが小さくなったからといって容量を値引きしない。
通常計画をlong実行へ渡せるかは、計算後のアダプターで正確に判定する。
巨大計画とbytesだけ巨大な計画は、既存BigInteger APIの側面データを付けて返す。
simulation計画は製作開始できないという既存契約を維持する。

## 9. 自動クラフト実行との接続

製作開始時は、AE2または外部CPUの既存受付で、実在庫・CPU容量・使用するパターンを確認して所有権を確保する。
T0後の在庫変更はこの受付の問題として扱い、計算途中へWorld照会を戻さない。
同時注文が同じ在庫を見て計画することは許す。実在庫を両方へ二重予約することは許さない。
不足時に新しい自動再発注ループを追加しない。利用側が持つ受付失敗・再計画の契約へ返す。

搬入出の実操作とReceiptはサーバー所有のまま。計画値からアイテムを生成しない。
数量がlongを超える時は、実行APIが受理する単位へ必要な時だけ分割し、未処理残量はBigIntegerで持つ。
巨大回数ぶんの子ジョブやリストを事前生成しない。
独自の投入速度上限やtick待機を追加せず、同じ定義の再解決、Map生成、重複検査を減らす。
通知の集約は正確な差分・所有者・Receipt IDを保持できるものに限る。

Mekanism/GTへのRecipe Intentは、Providerが選んだレシピ候補を渡す実行側の機能として扱う。
実機の入力適格性、電力、時間の確認は機械側に残す。
搬入出によるサーバー負荷を完全な0にはできないため、実操作の量を保って重複仕事を減らす。

## 10. 実装上の責務

以下は予定の所有単位。単純な値型を除き、同じ仕事を複数クラスで持たせない。

| 所有単位 | 仕事 |
| --- | --- |
| `PatternCatalog` | 登録情報と変換アダプター、世代付き不変定義、変更時の索引更新 |
| `OrderSnapshot` | T0の在庫・権限・可視性・定義参照。Worldへの逆参照なし |
| `GraphCompiler` | 到達グラフの共有、SCCと資源競合範囲、定数式と隣接配列 |
| `ExactPlanner` | 需要集約と全注文の会計。通常量と巨大量で同一入口 |
| `CoupledRegionSolver` | SMTInterpolへの局所整数制約と循環の順序構成 |
| `PlanResult` | 正確な数量、圧縮工程、選択した実入力、容量計算に必要な情報 |
| `Ae2PlanAdapter` | 既存のAE2計画・BigInteger API・表示への変換 |
| `ExecutionBridge` | 既存API呼出しを実行所有者へ渡す。計画の再探索をしない |

BigInteger APIの既存型は外側に残し、内部はこれらへ委譲する。
現行`NativeVmAccess`の計算中World待機、`VmInstructionExecution`の候補別再帰、
`VmDemandProgram`の都度適格性探索、ACO/VM間の二重計算・再選択は、新規注文の経路から退役させる。
公開型、旧保存データの読取、既存取引を完了・返却するためのコードは、移行根拠を確認してから整理する。

## 11. 受入条件

テスト件数ではなく、以下の入力と結果を根拠にする。

| 条件 | 確認する結果 |
| --- | --- |
| 第5節の共有Wと端数 | need=96、製造23回、使用W5・iron65、不足iron4、余剰W1 |
| `3 ore -> 2A+B`でA4/B2 | 製造2回、ore6、副産物二重計上なし |
| Aにiron/copper、Bにiron、各在庫1 | Aをcopper、Bをironへ割当。不足0 |
| 返却容器・触媒 | 種1個の再利用、種0個では開始不可、返却前の利用なし |
| NBT・耐久値・液体・chemical | キー、単位、遷移、返却が実際の定義と一致 |
| 中間数量またはbytesだけlong超過 | 根が1個でも全中間量と容量が正確 |
| パターン変更、同時注文 | 計算は各T0を保持。実行受付の二重予約なし |
| 取消・再起動 | 旧ジョブを含め、未受理入力だけ返却。受理済みReceiptを二重適用しない |

小規模の代替・循環グラフは、独立した全列挙モデルと数量・成立可否を比較する。
固定工程は手計算と直接式でも照合する。旧VMだけを正しさの基準にしない。
式の丸め、起動材、共有在庫を狙った反例を含める。

性能は実サーバーの同じパターン集合で、在庫なし・一部・十分を比較する。
至高量子制御回路は回帰用、クリエイティブ制御回路は最終目標用として別に記録する。
数量は1、2、10、50、100、1000、Long.MAX_VALUE、その+1、最終目標の正確な十進数を使う。
「922京」を922 × 10^16と読むと9,220,000,000,000,000,000で、Long.MAX_VALUE未満。
したがってこの注文の成功だけでlong超過対応を証明せず、中間量と別の境界注文も確認する。
AQE容量10^1024-1の等号・1 byte超過は、数量性能とは別に検査する。

計測範囲は要求受付から計画表示用データの完成まで。取得待ち、コンパイル、キュー待ちも含める。
cold/warmの両方、単独/同時注文、成功/不足を記録する。冷えた初回を隠さない。
在庫取得後のWorldアクセス0、枝ごとのグラフ再構築0、注文個数に比例するループ0を構造要件にする。
サーバー占有時間、ワーカーCPU、割当量、メモリ最大量を時間と併記する。
最終目標は全原料工程を含むクリエイティブ制御回路の指定数量で10秒未満。
参照用fixtureの高速化やライブラリの公表性能を、この実機受入の代わりにしない。

## 12. 実装への順序

1. API/保存互換の基準を固定し、実環境のパターン型と代表注文データを受入fixtureにする。
2. 純粋な`PatternDef`と`OrderSnapshot`、共有グラフ、固定工程の需要集約を実装する。
3. 実グラフの競合範囲でSMTInterpolを比較試作する。BigInteger直入力と正確な整数出力を使い、
   大きな結合領域でも実用時間に収まるかを確認する。遅い場合はグラフ縮約と式を再設計する。
4. 副産物・入力選択・返却・実在庫の競合を同じ会計へ統合し、循環の圧縮順序を完成させる。
5. AE2要求入口とAPI出口を接続し、選んだ順序を実行側へ渡す。新旧計算器を重ねて実行しない。
6. 実機で数量・時間・実行受付・取消・復旧・同時注文を受入し、その後に不要な旧内部実装を削除する。

これらは一つの完成品へ向けた実装順序であり、各段階を完成版としてリリースする計画ではない。
一般循環と動的パターンの対応、整数制約の実環境性能は、設計だけでは完了を主張できない。
